## Runtime investigation

Commands run (credential values omitted):

```powershell
docker compose ps --all
docker compose logs --no-color --tail 120 mysql backend
docker compose logs --no-color --tail 250 backend mysql | Select-String -Pattern 'ERROR|Exception|Access denied|Communications link failure|Caused by|Flyway|migration|Started Brandista|ready for connections'
Invoke-WebRequest http://localhost:8080/actuator/health -TimeoutSec 15
docker compose exec -T mysql sh -c 'mysql --protocol=TCP -h127.0.0.1 -u"$MYSQL_USER" -p"$MYSQL_PASSWORD" "$MYSQL_DATABASE" -N -e "SELECT version FROM flyway_schema_history WHERE success=1 ORDER BY installed_rank;"'
```

Observed evidence:

- Compose reported backend `Up` and MySQL `Up (healthy)` at inspection time.
- MySQL logs report MySQL 8.4.11 “ready for connections”.
- Backend logs report Spring Boot started on port 8080, but subsequent health/database access logs contain `java.sql.SQLException: Access denied for user 'brandista_app'@'172.18.0.x' (using password: YES)`.
- `GET /actuator/health` returned HTTP 503. The application process is therefore running but not healthy.
- An in-container application-user migration query also returned MySQL error 1045 (access denied); migration history could not be verified with the current credentials.
- The Compose health check only verifies that the MySQL server accepts a root ping; it does not verify that the configured application user can authenticate. `depends_on: condition: service_healthy` therefore does not guard against stale-volume credential mismatch.
- The existing volume is persistent. MySQL applies `MYSQL_*` initialization variables only to a fresh data directory. The observed failure is consistent with credentials changed after this volume's initial creation, not a demonstrated application/JDBC host or port error. Exact historical credential values are not logged here.
- The previously reported timeout is isolated to DB readiness/authentication as observed here: the health request completes with 503 rather than timing out; the database health check passes while backend DB health fails. Earlier backend log output includes failed datasource access during startup; the currently captured evidence points specifically to authentication failure. No destructive volume reset was performed.
- `docker compose logs` on the running instance predates the source-only CORS fix below; runtime recreation was intentionally not attempted while the local database credentials are mismatched.

Safe recovery: use the original credentials that initialized the existing `mysql_data` volume, or authenticate with a valid MySQL administrative credential and alter/create the `brandista_app` account to match the current local environment. Then restart/recreate only the backend and verify `/actuator/health` and migration history. Do not run `docker compose down -v` unless the local database is deliberately disposable and its data loss is accepted.

## Findings and changes

1. **Confirmed integration blocker — Compose dropped CORS configuration (fixed in source).** `SecurityConfiguration` consumes `brandista.security.cors.allowed-origins`, but `compose.yaml` did not pass `CORS_ALLOWED_ORIGINS` to the backend. Thus changing the documented `.env` value had no effect in Compose. Added that environment mapping. Allowed origin remains an explicit comma-separated allow-list; it defaults empty.
2. **Confirmed runtime blocker — stale MySQL volume credentials (environment-specific, not changed).** Runtime logs and health status prove database authentication failure. The current operator must restore/rotate credentials without destroying data.
3. **SRS unavailable.** README itself says no SRS/account policy document is present. Email-first login, no variants, flat categories, no default address, etc. cannot be certified against the unavailable SRS. See unresolved blockers.
4. **OpenAPI is not configured.** No OpenAPI dependency or generated specification exists. The implementation contract is recorded in `B0.14-api-contract.md` without adding a new runtime dependency.
