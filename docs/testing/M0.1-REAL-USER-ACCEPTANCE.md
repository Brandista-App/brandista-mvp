## Startup/restart commands

For normal owner use, start the services as detached background processes from PowerShell:

```powershell
Set-Location D:\uzair-brandista\repositories\brandista-mvp
.\scripts\start-m01-background.ps1
```

This starts Docker Desktop if needed, waits for the engine and application readiness, and launches the backend/frontend in hidden independent processes. Logs are in `target/m01-background-*.log`. Previously shared port-5175 links redirect to the MySQL app on 5176 when that older port is free. In particular `/brands/sample-studio` redirects to `/brands/demo-m01-lahore-loom`. No H2 fallback or mock response is used. Keep Docker Desktop running while testing. The earlier interactive foreground processes ended before a later loading attempt; this background launcher addresses that lifecycle problem.

Keep Docker Desktop's Linux engine running. Use two PowerShell terminals, with Java 21 and Node/npm installed. Docker commands require the normal user's Docker access; restricted sandbox access initially failed but the normal-user engine works.

Terminal 1, backend/database:

```powershell
Set-Location D:\uzair-brandista\repositories\brandista-mvp
.\scripts\start-m01-backend.ps1
```

The script creates `.env.m01` only if absent, generates database/JWT secrets without printing them, starts **only** the M0.1 MySQL service, verifies the application DB login, then runs the production jar at 127.0.0.1:8082. Flyway applies migrations V1–V8; Hibernate validates the schema. No customer or privileged application account is seeded. If the jar is missing, the script packages it; to rebuild intentionally, run `start-m01-backend.ps1 -Build`. Packaging uses `mvnw.cmd package -DskipTests`; run automated tests separately when needed. Keep `.env.m01` private and preserve it with the database; changing its password values does not alter an existing MySQL account.

Terminal 2, frontend:

```powershell
Set-Location D:\uzair-brandista\repositories\brandista-mvp
.\scripts\start-m01-frontend.ps1
```

This copies the sibling `brandista-mobile` source, configuration and unchanged lockfile into ignored `target/m01-frontend`, restores cached locked dependencies if needed, and starts Vite on **5176**, with `VITE_API_BASE_URL=http://127.0.0.1:8082/api/v1`. It avoids the original frontend's locked native dependency and does not overwrite its source or configuration. If offline installation lacks a cached package, run `npm.cmd ci --ignore-scripts --no-audit --no-fund` in `target/m01-frontend`, then rerun the startup script. No mock server, response interception, fixture fallback or authentication bypass is enabled. Fetch mocks exist only in automated `.test.*` files, which Vite's application entry does not import.

Once backend readiness is UP, initialize the **insert-only** catalogue from a third terminal:

```powershell
Set-Location D:\uzair-brandista\repositories\brandista-mvp
Invoke-RestMethod http://127.0.0.1:8082/actuator/health/readiness
.\scripts\seed-m01-catalogue.ps1
```

Seeding checks that it is connected to `brandista_m01` with all eight migrations, then inserts only missing demo slugs. It creates no users, updates no existing catalogue rows and deletes nothing. Rerunning it was verified to retain exactly two demo brands/four demo products without duplication.

The agent left the M0.1 Java process, MySQL container and Vite process running at handoff. Terminal-based commands above reproduce the environment if those processes later end. Stop the foreground Java/Vite processes with Ctrl+C in their terminals. To stop the dedicated database while preserving its volume:

```powershell
docker compose --env-file .env.m01 -p brandista-m01 stop mysql
```

Do **not** run `down -v`, delete volumes, reset credentials, or use the earlier H2 launcher for this acceptance test. Re-run the backend script after a normal stop; do not start a second Java process while 8082 is already occupied.

## Inspected implementation and API

No authoritative SRS was found in the four checked-out repositories; formal SRS conformance remains BLOCKED. `brandista-docs`/`brandista-admin` contain only Git metadata. Source and `B0.14-api-contract.md` establish these actual contracts:

| Action | Endpoint / behavior |
| --- | --- |
| Register | POST /api/v1/registrations with email/password; creates CUSTOMER, ENABLED |
| Login | POST /api/v1/auth/login; returns bearer JWT and safe identity |
| Brands | GET /api/v1/brands; active-brand array |
| Categories | GET /api/v1/categories; paginated active categories |
| Products/detail | GET /api/v1/products with keyword/brandId/categoryId/sort/page/size; GET /products/{slug} |
| Read/add cart | GET /api/v1/customers/me/cart; POST /cart/items with productId/quantity |
| Change/remove | PATCH /api/v1/customers/me/cart/items/{itemId}; DELETE same item route |
| Clear | DELETE /api/v1/customers/me/cart/items |
| Addresses | Customer-scoped /api/v1/customers/me/addresses CRUD API; frontend read-only |
| Checkout/order/history/payment | No controllers, schema or supported business flow; /checkout frontend redirects to cart |

Authentication uses BCrypt, normalized unique email and signed HS256 bearer JWTs. Password policy is at least 12 Unicode characters and at most 72 UTF-8 bytes. No role is accepted in public registration. Tokens stay in frontend memory; refresh/full navigation **ends frontend authentication by design**, while the database customer/cart remains saved. In-app navigation preserves login. Sign-out clears the local token and protects routes; it does not revoke an already issued bearer token server-side. Access tokens expire after the configured 15 minutes. CORS allows the exact 127.0.0.1:5176 origin; no security mechanism was disabled.
