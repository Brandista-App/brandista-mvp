# Production owner provisioning: inspection findings

Inspected 2026-10-28 before implementation, base `b5f6d5d` (origin/main).

- `User`, V1 and V9: unique normalized email, BCrypt `password_hash`, independent CUSTOMER/ADMIN base role, ENABLED/DISABLED status. No automatic production seeding.
- V10: explicit `user_platform_grants` with `SUPER_ADMIN`; V11: permanent bootstrap lock/marker and audit events. V12-V14 extend memberships/invitations/orders. Existing migrations must not be edited or replayed.
- `LoginController` / `LoginService`: POST `/api/v1/auth/login`; JWT HS256 issuer/audience/expiry validation. Response `account.role` is the base role. Live DB authority lookup in `CurrentAccountAuthorities` determines the platform grant; a client role claim cannot grant access.
- `SecurityConfiguration` and `SuperAdminIdentityController`: `/api/v1/super-admin/identity` requires SUPER_ADMIN at URL and method layers. Other admin endpoints accept legacy ADMIN or SUPER_ADMIN.
- Admin frontend `src/auth/session.ts` (local deployment audit checkout): admin-mode login requires matching account ID and `platformGrants` containing SUPER_ADMIN from the identity endpoint. A CUSTOMER login response is expected for a newly provisioned custodian.
- `PasswordEncoderConfiguration` supplies BCrypt. `PasswordPolicyValidator`: at least 12 Unicode code points and at most 72 UTF-8 bytes; no composition rule. Recommend a unique password-manager generated password. Do not invent a conflicting password policy.
- `BootstrapMain` and `OperatorProvisioning` already implement interactive masked passwords, confirmation, explicit create/grant/reset modes, separate disabled-by-default recovery gate, transaction serialization, audit rollback, duplicate protection and last-custodian protection. Existing PR2 PowerShell runbook and disposable MySQL script are reusable.
- `INITIAL_CREATE` rejects an existing normalized email without changing it; any historical grant or initialization marker prevents repeated initial bootstrap. Existing-account grant/reset requires both email and numeric ID. Never switch to recovery automatically after rejection.
- Production docs identify Render `brandista-mvp`, Aiven database `brandista`, runtime identity `brandista_app`, VERIFY_IDENTITY and service-specific CA. They do not supply approved operator credentials or establish current live state. Use a separate least-privilege operator identity.
- No public password-reset endpoint, reset-token table or password-reset mail delivery is present in this revision. Invitation delivery is a different purpose. This change uses the task's administrator-assisted recovery fallback, not a claim of operational email recovery. Token expiry/single-use tests are not applicable to that fallback.
- Existing `OperatorProvisioningIntegrationTests`, `OperatorConfigurationTests`, login and privileged-identity tests cover initial provisioning, duplicates, wrong IDs/roles, authorization, hash validation and recovery gates. Add an end-to-end reset/login regression and safe persisted-state inspection tests.
