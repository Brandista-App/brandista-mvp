## Authentication, authorization and isolation

JWT uses HS256 with a decoded key of at least32 bytes, configured issuer/audience and15-minute default lifetime. Signature, issuer, audience and expiry are validated. Each authenticated request resolves the enabled account and live platform grants from the database; client role claims do not grant super-admin authority. Account/grant revocation and merchant brand membership are checked at current DB state. These checks cost queries under load; do not cache them without an explicit revocation design.

Passwords are BCrypt encoded and login errors are generic. The API uses stateless Authorization bearer headers, not browser-managed session cookies; disabling CSRF depends on retaining that boundary. Exact-origin CORS rejects wildcard configuration and does not enable credential cookies. Do not switch to cookie authentication without a new CSRF/session assessment. Privileged MFA/account-aware brute-force controls and a distributed login limiter are not implemented. The new proxy IP limits mitigate one boundary only and cannot protect a directly reachable backend or coordinated attacks.

Provisioning is an offline interactive entry point outside the web scan, with controlled service flags, persistent initialization lock, protected recovery and audited operations. There is no bootstrap HTTP API or automatic production super-admin. The PROD-001 disposable fixture invokes that same `INITIAL_CREATE` service with synthetic data and test-only enablement; this is not an owner terminal/production provisioning claim. The interactive CLI itself remains **NOT VERIFIED in this run**. Secrets must never be passed as CLI arguments, logged, checked into Git or sent through an HTTP fixture endpoint.

Brand invitations use recipient-email binding, hashed expiring one-use tokens, current grants, DB-backed acceptance quotas and audits. Development encrypted delivery is isolated by profile and rejects production activation. Default production delivery fails closed: **no real invitation email adapter is configured**. In-memory capture in tests is an authorized synthetic transport, not delivery infrastructure.

Checkout serializes per-customer changes, locks products in ID order, verifies current brand/category/publication/stock state, commits stock/order/cart/fulfillment together and returns immutable snapshots. A unique customer/key pair plus request hash supports same-request replay and rejects key reuse for a different review. Cross-brand order visibility is based on immutable order lines, not mutable catalogue ownership. Merchant transitions use fulfillment locks/version checks and retain parent COD/UNPAID financial state. Automated and load integrity evidence is recorded separately; do not call DELIVERED a paid order.

## Operational boundaries and open gates

Production metrics are on a separate loopback listener and denied on the app listener. Ready/liveness probes use `/readyz` and `/livez`; proxy `/healthz` targets readiness. Structured ECS logs add machine-readable context but do not automatically redact arbitrary exception messages. No request/response payload logging is added. Restrict log access, normalize query digests, avoid PII/high-cardinality tags and verify representative failure logs before public operation.

The production-like template is read-only/non-root for the app, drops capabilities, limits memory/PIDs and uses no-new-privileges. Its MySQL URL requires operator-provided identity-verifying TLS and appropriate driver timeouts; no real provider certificate/DB grant is validated here. Runtime root is forbidden. The isolated load fixture uses root only inside a newly created disposable database/container to migrate, seed, inspect and restore synthetic data; this is not a production least-privilege test.

There is no approved public HTTPS service, deployed CORS/CSP/headers policy, remote backup vault, running notification/on-call channel, immutable image digest pinning or complete secret-history scan demonstrated by this milestone. A tracked-file check is not a history/credential-vault audit. Secret rotation, signing-key custody, customer-data retention/access and backup access need assigned owners and actual staging verification.

Android's current showcase signing and the unsigned **Simulator-only** iOS artifact are internal test evidence. Neither proves production app-store identity or physical iPhone installation. Personal Team provisioning and actual device tests remain owner hardware/account gates; no Apple credentials or signing assets are requested or generated here.
