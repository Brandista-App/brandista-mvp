# F0.9 Founding Brand Pilot — Implementation Plan

## Audit snapshot

- The backend is Java 21 / Spring Boot 3.5 with MySQL, Flyway, JPA, bearer JWT authentication, and H2 integration tests.
- The backend has administrator-only brand CRUD. A new brand is immediately `ACTIVE`, and public brand discovery shows active brands. This does not represent an application or review workflow.
- The backend has administrator-only product CRUD and `DRAFT`, `PUBLISHED`, `UNPUBLISHED`, and `DEACTIVATED` states. Draft products are excluded from public discovery. Product records support name, slug, description, brand/category references, PKR price, and availability. There are no SKU, image storage/upload, size/colour variants, quantity inventory, or order/checkout capabilities.
- All brand and product writes require `ADMIN`; there is no merchant account role or tenant-scoped brand editing.
- The frontend is React 19, TypeScript, Vite, and React Router. It is a customer storefront with discovery/auth/cart routes. There is no merchant application or admin interface.
- The repositories contain no standalone SRS document. Existing backend documentation describes unresolved choices around product image storage, variants, and stock; binding pilot terms therefore need project-owner review.
- F0.8 reports were reviewed on the separate F0.8 PR branches in `brandista-mobile/docs/deployment`. They establish local rehearsal documentation but no remote staging host and document frontend check limitations; no remote pilot environment is available from this audit.

## Minimum workflow proposed

1. A prospective brand submits a public interest form with brand name, contact name, email, and optional website/message.
2. The application is stored separately from the customer-facing brand catalogue in `SUBMITTED` status.
3. An administrator-only API lists applications and records `NEEDS_INFORMATION`, `APPROVED`, or `REJECTED`, with a review note and timestamp.
4. Approval creates a separate `INACTIVE` brand record. An administrator verifies the brand profile and activates it through the existing brand API when ready.
5. Operators use the existing admin product API to enter a product in `DRAFT`, review it, and explicitly publish it. Public discovery continues to require a published product and active brand/category.
6. Operators check the public brand/product storefront and the pilot checklist before inviting customers.
7. The project owner and brand record pilot feedback, incidents, and outcomes using the supplied checklist/runbook.

## Assumptions requiring owner review

- No SRS onboarding requirements were present in either repository. These proposed fields and state transitions are a narrow MVP workflow, not legal or commercial policy.
- No merchant accounts are introduced. The first pilot is operator-managed; only existing `ADMIN` users may review applications or manage brands/products.
- Approval records an operational decision; it is not legal verification or a signed commercial agreement. Approved brands are created inactive pending profile verification.
- Duplicate open applications are checked by normalized contact email. Name similarity is not treated as proof of a duplicate; an operator checks possible duplicates. The email check can race under concurrent requests and needs database-backed hardening before broader exposure.
- Product images remain deferred because there is no durable image storage provider. The intake CSV, if used, is explicitly a collection template and not an importer.
- Payment, shipping, returns, cancellations, refunds, fulfilment, stock quantities, and order history remain unsupported.

## Implementation scope

- Add a Flyway migration and public application submission endpoint plus administrator-only list/review endpoints.
- Enforce server-side validation, duplicate-open-application handling, status transitions, review timestamps, and inactive brand creation on approval.
- Add focused backend integration coverage for validation, duplicate submissions, access control, decisions, and storefront visibility.
- Add a customer-facing partner-interest form and API call. It collects no credentials or sensitive identity documents and does not expose review operations.
- Provide operator runbook, intake template, pilot checklist, verification report, and deployment/staging caveats.

## Out of scope

Merchant logins, self-service product management, image upload/storage, bulk import, inventory quantities/variants, order/payment/fulfilment features, legal verification, and deployment to an unavailable staging service.
