# Brandista F1.0 — Order Operations Runbook

## Current system boundary

**Brandista does not currently accept or create orders.** There is no checkout/order API, order database table, payment integration, fulfilment state machine, customer order history, or inventory reservation. The frontend checkout is disabled. This runbook documents the safe boundary and future manual responsibilities; it is not authorization to transact.

## Current cart behavior (software-supported)

- An authenticated CUSTOMER cart belongs to the current principal; clients cannot select another customer's cart.
- Adding an item requires a product that is published and marked available, whose brand and category are active.
- Quantities must be positive integers and cannot overflow the supported integer range.
- Cart prices and subtotals are calculated by the backend using the current product price. The cart is not a price quote, reservation, or order.
- If a product, brand, or category later becomes unavailable, the cart can report the item as unavailable; no order is created and no stock is deducted.
- No order confirmation, cancellation, refund, shipment, delivery, or customer order status is generated by the software.

## Manual responsibilities if a separate, owner-authorized pilot policy is approved

These steps must remain outside Brandista until appropriate software and policy exist. Assign named people and contact channels before any real order activity. Do not improvise payment collection or claim that an order is accepted through the application.

1. **Receive and validate a request:** Record it only in an owner-approved secure process. Confirm whether it is a test inquiry or a real purchase request. Brandista currently has no valid order record to receive.
2. **Confirm product and price:** Contact the authorized brand representative and confirm item identity, current price, availability, variant/size if relevant, and permission to sell. The application does not track quantities or variants.
3. **Confirm customer terms:** Before accepting any real transaction, the owner and participating brand must define and communicate payment, delivery, cancellation, returns, refunds, complaints, privacy, and support terms. No timeline or refund promise is supplied by Brandista.
4. **Communicate status:** Use the agreed approved channel and record who communicated what and when. Do not represent a cart as a confirmed order.
5. **Handle stock discrepancy:** Stop offering the affected item; an authorized operator can mark its availability `UNAVAILABLE` or unpublish it through existing admin APIs. Verify public discovery after the change. This is a manual catalogue flag, not a reservation or count.
6. **Handle cancellation/return/refund/complaint:** Follow only the written owner/brand policy. Escalate unresolved, safety, privacy, payment, or rights issues to the named owner. The application has no cancellation, return, refund, or complaint workflow.
7. **Record outcome:** Use the scorecard only after defining a privacy-safe owner-approved recordkeeping method. Label synthetic test records separately from real customer activity. Do not store payment credentials or unnecessary personal data.
8. **Pause:** The owner/operator should pause affected listings or all pilot invitations if stock, price, product rights, privacy, security, or support cannot be confirmed. Record reason, owner, time, affected listings, and restart approval.

## Test-only operating procedure

For internal verification, use an isolated local/test database, disposable test CUSTOMER account, and synthetic catalogue records. Exercise browse and cart only. Do not attempt checkout, send goods, collect payment, or create a real customer order. Remove test records only using an explicitly isolated test environment and its documented reset procedure; never remove or reset a shared/persistent database volume as a shortcut.

## Go/no-go rule

Until an order API and owner-approved manual policy exist, the only supported pilot is a non-transactional catalogue demonstration, and that remains blocked by absent staging, unavailable MySQL runtime verification, blocked frontend build/tests, and unresolved brand/privacy agreements. A real sale or fulfilment is **NO-GO**.
