# F0.9 Founding Brand Pilot — Verification Report

**Assessment:** The backend onboarding workflow and H2 migration/tests are verified. Frontend checks and Docker/MySQL runtime verification are blocked in this environment. A controlled founding-brand pilot is **not ready** until those checks, staging, operational agreements, and a workable product image/content process are resolved.

## Capabilities found before changes

- Backend admin-only brand CRUD creates brands directly as `ACTIVE`; public listing contains active brands only.
- Backend admin-only product CRUD creates `DRAFT` products and supports explicit publish/unpublish/deactivate. Public discovery requires a published product with active brand and category.
- Existing product fields are name, slug, description, brand/category IDs, PKR price, and availability. There is no SKU, image storage/upload, variant/quantity stock, merchant role, tenant-scoped ownership, orders, or checkout.
- Frontend is a customer storefront with catalog, accounts, and cart, but no admin or merchant interface.
- No standalone SRS was present in either checked repository. Backend docs describe open product decisions. Pilot policies are therefore proposed assumptions requiring owner review.
- Reviewed the reports on the separate F0.8 branches in both repositories. They document local-only rehearsal preparation and no provisioned public staging service; the F0.8 PR branches were left unchanged.

## Changes implemented

- Added `V8__create_brand_applications.sql` and an application entity with `SUBMITTED`, `NEEDS_INFORMATION`, `APPROVED`, and `REJECTED` states, contact/business fields, reviewer note/timestamp, and optional link to the created brand.
- Added public application submission (`POST /api/v1/brand-applications`) with required brand/contact/email, optional validated HTTP(S) website and message, normalized email, and duplicate-open-email conflict response. Public receipt omits contact details.
- Added admin-only list and review endpoints. Approval creates an `INACTIVE` brand, keeping application approval separate from profile verification and storefront activation. Terminal decisions cannot be changed.
- Added integration tests for submission validation, duplicate handling, role access, approval/inactive visibility, request-information/rejection transitions, invalid decisions, closed records, and slug conflict.
- Added the customer-facing `/partners` form with success/error states, field-error display, frontend API client support, and focused UI tests. It explicitly states that submission does not approve or activate a brand.
- Added an operator runbook, pilot checklist, and CSV intake worksheet. The CSV is **not** an import format.
- Updated `B0.14-api-contract.md` with the actual F0.9 routes, request/response shapes, authorization, states, and limitations.
- No merchant account, admin frontend, product image handling, bulk import, payment, or order capability was introduced.

## Workflow status

- Public application capture, authenticated admin review endpoints, and customer form: **implemented; backend automated coverage passed**. Frontend UI tests remain blocked by unavailable local npm executables.
- Approved brand creation: creates inactive brand pending operator verification and activation.
- Product intake: manual entry through existing admin API; CSV is only a worksheet.
- Product images: unsupported pending durable storage selection.
- Partner consent, commercial terms, legal review, and fulfilment/payment processes: manual owner/partner tasks; none claimed complete.

## Outstanding blockers

- **High — frontend verification blocked:** frontend typecheck, tests, lint, and build have not run because `node_modules` executables are absent.
- **High — staging unavailable:** no remote staging URL/environment has been provisioned; do not onboard a real partner into a public pilot yet.
- **High — pilot operations unresolved:** written scope, prices, fulfilment, returns/refunds, support ownership, data privacy review, and success measures require owner/partner agreement.
- **High — public submission endpoint has no rate limiting or abuse controls.** Keep exposure controlled until protections are added and verified.
- **Medium — no admin web console:** operators must use the authenticated API with an authorized administrator account.
- **Medium — images, SKU, variants, and quantity inventory are not implemented.** Confirm that pilot products can be represented without these fields before agreeing to scope.
- **Medium — duplicate-open-email detection is application-level and can race under concurrent submissions; current MVP has no database-enforced conditional uniqueness.**
- **Low — accepted application data contains contact PII.** Apply project-owner retention and deletion/access policies before real partner intake.

## Readiness decision

- Backend workflow internal testing with synthetic data: **PASS** for H2 integration/regression tests; do not interpret this as MySQL runtime verification.
- Full frontend internal testing: **BLOCKED** pending local npm dependencies and successful checks.
- Controlled founding-brand pilot: **BLOCKED** pending passing tests, accessible staging, abuse controls, owner/partner agreement, and a workable image/content process.
- Public production launch: **NOT READY**.
