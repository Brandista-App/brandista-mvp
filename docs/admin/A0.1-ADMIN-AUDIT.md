# A0.1 — Administration and brand management audit

Audit date: 16 October 2026 (Asia/Karachi). Backend baseline `c6c0420`; customer web baseline `b90cee9`. Inspected local repository trees, Spring configuration/services/controllers, migrations V1–V9, tests, and the dedicated local MySQL database. This is an implementation audit, not approval of a production administration policy.

**Result: global-admin catalogue APIs work, but the complete administration workflow is not ready.** There is no production first-admin provisioning, no super-admin/brand-admin distinction, no user-to-brand membership, and no administration application. Successful customer acceptance does not verify these missing workflows.

Owner direction during this audit: **define super-admin and brand-scoped admin permissions before implementation**. The proposed permissions below are a reviewable specification; they have not been added to the database, JWTs, public registration, or UI. No application architecture changes, real account provisioning, deployment, or Android development were performed.

## Existing API surface

Base `/api/v1`. ADMIN routes require a valid ADMIN bearer token through both URL rules and controller method authorization. CUSTOMER cannot administer brands/catalogue. There is no merchant identity or tenant filter.

| Access | Method and path | Behavior |
| --- | --- | --- |
| Public | `POST /registrations` | Customer only; no role selection |
| Public | `POST /auth/login` | Shared authentication for existing enabled accounts; returns token/account role |
| Public | `GET /brands` | Active brands array; no public brand detail endpoint |
| Public | `GET /categories?page=&size=` | Active categories page |
| Public | `GET /products?page=&size=&keyword=&brandId=&categoryId=&sort=` | Published eligible catalogue; sort `default`, `price_asc`, `price_desc`; size 1–100 |
| Public | `GET /products/{slug}` | Eligible published product or 404 |
| Public | `POST /brand-applications` | Contact/intake only; not user registration |
| ADMIN | `POST /admin/brands`; `GET /admin/brands`; `GET /admin/brands/{id}` | Create active brand, list all, read |
| ADMIN | `PUT /admin/brands/{id}`; `PATCH /admin/brands/{id}/deactivate` | Metadata/status edit, soft deactivate |
| ADMIN | `POST /admin/categories`; `GET /admin/categories`; `GET /admin/categories/{id}` | Create, paged list, read |
| ADMIN | `PUT /admin/categories/{id}`; `PATCH /admin/categories/{id}/deactivate` | Edit/status, soft deactivate |
| ADMIN | `POST /admin/products`; `GET /admin/products`; `GET /admin/products/{id}` | Create draft, paged list, read |
| ADMIN | `PUT /admin/products/{id}` | Full editable details; includes brand/category references, price and availability |
| ADMIN | `PATCH /admin/products/{id}/publish`, `/unpublish`, `/deactivate` | Publication/soft removal lifecycle |

| CUSTOMER | `/customers/me/addresses`, `/cart`, `/checkout/*`, `/orders` | Existing customer-only features; not administration or merchant fulfilment APIs |

Missing API capabilities (names intentionally not invented as existing routes): private first-super-admin provisioning/recovery; admin identity/profile and account lifecycle; invite/accept/expire/revoke; membership list/assign/remove; brand-scoped catalogue reads/writes; admin session invalidation; product media upload/manage; audit-history reads. Hard delete, bulk import, inventory ledger and category ownership require scope decisions. No public admin registration is proposed.

## Frontend and repository inventory

Findings apply to these local checkouts; uninspected remote branches are not claimed to contain nothing.

Missing screens: admin login/session-expired/logout; first-admin operator instructions; dashboard; brand list/create/edit/status; application review; member/invitation management; catalogue list/create/edit/publication; stock adjustment; image management; audit history. Brand-admin screens additionally need server-side scope enforcement before they are useful. Hiding controls alone cannot authorize access.

## Security and permission gaps

| Priority | Finding | Consequence / next control |
| --- | --- | --- |
| High | JWT authorities come from the signed role claim without checking current database role/status on admin requests. Login rejects disabled accounts, but already-issued admin tokens retain authority until expiry. | Disabling, deleting or demoting an admin is not immediate revocation. Source-confirmed; no live-account exploit performed. Require fresh account/membership validation or a defined revocation mechanism before administrative onboarding. Default token lifetime is 15 minutes; configurable. |
| High | Existing ADMIN is global; no ownership relationship or scoped object checks. | Never issue current ADMIN to an external brand operator. Cross-brand access would be allowed by design. Add and test tenant scope before enabling brand logins. |
| High | No trusted production provisioning or recovery path. | Real administration is blocked despite passing fixture tests. Do not solve this with public role selection, committed credentials or a repeatedly enabled startup seed. |
| Medium | No persistent administrative action attribution/audit trail. Application review stores time/note, not reviewer ID. Stock setter overwrites count without reason/history. | Cannot reliably explain who changed publication, stock, role or brand status. Specify required actor/event records. |
| Medium | Public login/registration/intake have no application rate limiter/MFA/email verification flow. | Brute-force/spam protection and privileged authentication policy need definition before public administration exposure. No external gateway protection was verified. |
| Medium | Application duplicate-open check and review use ordinary reads without a review lock/version; no unique open-application invariant in migration. | Concurrent requests need dedicated tests and appropriate transaction/constraint handling before operational reliance. Potential race from source, not an executed exploit. |
| Medium | Brand logo reference accepts a bounded string without URL/storage policy; product media absent. | Define accepted reference schemes, trusted storage, MIME/size checks and authorization before adding rendering/upload. No server-side fetch/SSRF endpoint was found. |
| Medium | Catalogue edit/publication paths have no optimistic version and use ordinary reads; stock setter/checkout lock products. | Concurrent catalogue edits and checkout deserve MySQL regression testing before multiple operators use the console. No lost-update exploit claimed. |

Existing protections: BCrypt, parameter validation, unique constraints, foreign keys, stateless bearer authentication, exact-origin CORS without credentials/wildcards, issuer/audience/signature/expiry validation, safe error responses, CUSTOMER-only public registration, ADMIN-only management, publication filtering, transactional checkout and stock locking. These do not substitute for merchant isolation.

## Proposed permission definition — review before implementation

This proposal follows the owner's choice to define permissions first. `SUPER_ADMIN` and `BRAND_ADMIN` below are conceptual target permissions, **not implemented role values**. The current enum/database check/JWT converter only support CUSTOMER/ADMIN. Existing ADMIN should be treated operationally as platform staff until an explicit migration plan is approved; do not silently rename or grant it to merchants.

| Capability | Super-admin (proposed) | Brand admin (proposed) | Customer / public |
| --- | --- | --- | --- |
| First privileged account / privileged recovery | Trusted private operator procedure only; no public signup | Denied | Denied |
| Create/activate/deactivate brands; review applications | All brands | Denied; may view assigned brand | Public sees active metadata only; may submit intake |
| Invite/assign/remove brand admins | All brands; explicit audited assignment | Denied in initial milestone | Denied |
| Grant/revoke super-admin privileges | Private reviewed operator procedure initially; no normal dashboard action | Denied | Denied |
| Edit brand identity/status/slug | Platform staff only initially | Denied initially; later profile fields require approval | Denied |
| Manage shared category taxonomy | Platform staff only | Read active categories | Read active categories |
| Create/read/edit draft products | All brands | Active assigned brands only; server binds/validates brand | Published eligible products only |
| Publish/unpublish/deactivate products | All brands | Proposed: assigned brands only, subject to owner approval of publication policy | Denied |
| Set stock | All brands, audited | Assigned brands only, audited | Read public count; purchase through checkout only |
| Upload/manage product media | All brands after media policy | Assigned brands only after media policy | Read approved public images |
| Read application contact PII / platform audit log | Platform staff only | Denied | Denied |
| Read customer orders/delivery PII | Outside this milestone; define fulfilment privacy separately | Denied initially | Customer sees own orders only |

Scope rules proposed for approval: deny by default; server checks enabled account and active membership on every privileged operation; do not trust a client brand ID or long-lived brand claim alone; list queries must be scoped as well as detail/write routes; foreign-brand IDs must not reveal private objects. A product transfer to another brand must be super-admin-only. Removing a membership or disabling a brand immediately removes merchant write access. Invitation acceptance never converts public customer registration into a privilege-granting endpoint.

Unresolved owner decisions before implementation:

1. May one person administer multiple brands and also retain a customer account? This determines how the existing scalar role can evolve safely. Recommended behavior: independent explicit brand memberships, with customer access preserved; implementation shape requires an approved change.
2. May brand admins publish directly, or only submit drafts for super-admin approval? The table proposes direct scoped publication for a minimal workflow; it is not yet approved.
3. Who may invite/remove members and recover the first privileged account? Proposed initial boundary: trusted platform operator only; no merchant-to-merchant invitations.
4. Invitation delivery, expiry, one-time redemption and verified email policy; acceptable privileged authentication/MFA requirements; account removal/revocation expectations.
5. Confirm initial brand profile edit restrictions and product deactivation versus permanent deletion; define approved image storage/rights/limits before image functionality.

## Minimal implementation sequence

1. Approve the permission matrix and decisions above. Reconcile with the authoritative SRS if supplied; do not claim the checkout addendum approves new admin roles.
2. Implement and test private, explicit first-super-admin provisioning and privileged request revocation. No public admin signup, no role fields in customer registration, no default credentials, no automatic production seed. Choose operator account identity at execution time; do not modify real users during an audit.
3. Implement scoped brand memberships and one-time onboarding under the approved model, including removal and cross-brand negative tests. Update enum/schema/JWT policy only as an explicit reviewed architecture change.
4. Verify the real MySQL administration API workflow with isolated fictional fixtures: provision→login→brand→assign→category/product draft→stock→publish→customer discovery→unpublish/deactivate→remove member→confirm denied. Validate rollback/concurrency and capture sanitized evidence. Current audit did not mutate real MySQL to simulate this.
5. Build the smallest admin web app only after its permissions work: privileged login, brand/application management, members, draft/product edit, stock, publication and visible error states. Add global dashboard summaries later. Admin repository currently needs initialization; do not assume a ready shell.
6. Add approved media support and run owner administration acceptance before Android work depends on these capabilities. No deployment is authorized here.

**Smallest safe step completed now:** a repeatable integration test of the existing global-admin API lifecycle and inventory authorization, without introducing production roles/endpoints or provisioning real accounts. Functional onboarding implementation is BLOCKED pending the owner's permission-policy decisions, as requested during the audit.
